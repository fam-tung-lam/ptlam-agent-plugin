# The Pigeon Boundary and Mappers

This reference owns the Dart side of the platform channel: which file is the
contract, which is generated, how to regenerate, and how a mapper is named,
directed, and placed. The Kotlin and Swift halves belong to
`ptlam-code-style-kotlin-health-connector` and
`ptlam-code-style-swift-health-connector`.

## Contract, generated output, and hand-written code

| File                                                                               | Status                            |
| ---------------------------------------------------------------------------------- | --------------------------------- |
| `packages/health_connector_hc_android/pigeon/health_connector_hc_android_api.dart` | The contract — edit this          |
| `packages/health_connector_hk_ios/pigeon/health_connector_hk_ios_api.dart`         | The contract — edit this          |
| `packages/<platform>/pigeon/copyright_header.txt`                                  | Prepended to every generated file |
| `packages/<platform>/lib/src/pigeon/*_api.g.dart`                                  | Generated — never hand-edit       |
| `packages/<platform>/lib/src/mappers/**`                                           | Hand-written                      |
| `packages/<platform>/lib/src/health_connector_*_client.dart`                       | Hand-written                      |

Each contract file opens with `@ConfigurePigeon(PigeonOptions(...))` naming
`dartOut`, the native output path, `copyrightHeader`, and `dartPackageName`.
Change an output path there, not in a build script. The generated Dart carries
`Autogenerated from Pigeon (v26.1.0), do not edit directly` and a broad
`// ignore_for_file:` line; the lint package also excludes `**/*.g.dart` from
analysis, so a generated file is invisible to `melos run analyze:dart:strict`.

## Regenerate both platforms at once

Run `melos run pigeon` from the repository root. It runs
`dart run pigeon --input pigeon/<name>_api.dart` in each platform package,
patches the generated Swift with
`packages/health_connector_hk_ios/scripts/add_public_keyword_to_swift_code.py`,
then runs `melos format`. Regenerating one package by hand skips the Swift patch
and the formatting, so use the script.

Commit the regenerated `*.g.dart` with the contract change. The melos `version`
hook reruns `melos run pigeon` before a release commit, so a stale generated
file shows up as an unexpected diff at release time.

## Name a DTO and its mapper

Every Pigeon class and enum ends in `Dto`: `StepsRecordDto`, `MetadataDto`,
`HealthDataTypeDto`, `AggregationMetricDto`. A DTO carries only plain types —
epoch milliseconds for a `DateTime`, `double` for a measurement unit, `String?`
for an id.

A mapper is a pair of extensions in one file named `<subject>_mapper.dart`:

```dart
/// Converts [StepsRecord] to [StepsRecordDto].
@sinceV1_0_0
@internal
extension StepsRecordToDto on StepsRecord {
  StepsRecordDto toDto() { ... }
}

/// Converts [StepsRecordDto] to [StepsRecord].
@sinceV1_0_0
@internal
extension StepsRecordDtoToDomain on StepsRecordDto {
  StepsRecord toDomain() { ... }
}
```

`<Type>ToDto` declares `toDto()` and runs domain to platform.
`<Type>DtoToDomain` declares `toDomain()` and runs platform to domain.
`toDomain()` builds the record through its `.internal` factory so platform data
is not re-validated. Both extensions carry `@sinceVx_y_z` and `@internal`, and
import the exact symbols they need with `show`.

## Where a mapper file goes

Under `lib/src/mappers/` in the platform package that owns the DTO:

| Subdirectory                    | Holds                                                             |
| ------------------------------- | ----------------------------------------------------------------- |
| `health_record_mappers/`        | One file per record type, in the same family folder as the record |
| `metadata_mappers/`             | `Metadata`, `Device`, `DeviceType`, `RecordingMethod`             |
| `permission_mappers/`           | Permission requests, statuses, and permission lists               |
| `request_and_response_mappers/` | Read, aggregate, and delete requests, and their responses         |
| `exception_mappers/`            | `HealthConnectorException` and `HealthConnectorErrorCode`         |
| `health_data_sync/`             | Sync tokens and sync results                                      |
| `mappers/` root                 | Config, log, health data type, and platform feature mappers       |

An enum gets its own mapper file with an exhaustive `switch` in each direction,
never a `values[index]` lookup: the two enums are independent contracts and may
diverge in order.

## Register in the dispatcher, with explicit invocation

`health_record_mappers/health_record_mapper.dart` holds `HealthRecordToDto` and
`HealthRecordDtoToDomain`, which `switch` over every record type. A new record
needs a new `case` there and an import at the top of that file.

Write each case as an explicit extension invocation:

```dart
case final StepsRecord record:
  return StepsRecordToDto(record).toDto();
```

Never `record.toDto()`. With implicit invocation, a missing import silently
resolves back to the dispatcher's own `toDto()` and recurses forever at runtime;
the explicit form fails to compile instead. The dispatcher's doc comment states
this rule, and it applies in both directions.
